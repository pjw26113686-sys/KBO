# KBO 분석 · 스코어 예측 · EV 베팅 시스템

KBO 경기의 **승패 / 오버언더 / 핸디캡**을 포아송 결합 모델로 예측하고, 시장 배당과
비교해 **EV(+) 베팅 후보**를 가려낸다. 설계서 모듈 3~6(예측 모델 · EV 엔진 · 백테스트)을
**합성 데이터 N경기 시뮬레이션**으로 end-to-end 검증하는 코어가 구현되어 있다.

> ⚠️ 전제(설계서 §0): 스포츠 베팅에서 안정적 +EV 는 매우 어렵다(북메이커 마진 4~7%,
> 시장 효율성). 이 시스템의 목표는 "이기는 보장"이 아니라 **체계적으로 검증 가능한
> 가설 생성기**다. 백테스트/캘리브레이션 통과(GO) 전에는 실전 신호를 보내지 않는다.

## 왜 시뮬레이션인가

실전 검증의 전제인 크롤러(Statiz/KBO 라이브 스크래핑)는 봇 차단·법적 회색지대라
이 환경에서 동작 검증이 불가능하다. 대신 **우리가 '진짜' 팀 강도·구장·투수를 만들고**
몬테카를로로 경기를 생성한 뒤, 모델이 (노이즈 낀 관측만으로) 그 구조를 회수하고
시장을 이길 수 있는지를 수치로 판단한다.

## 빠른 시작

```bash
pip install -r requirements.txt

# SQLite 스키마 초기화 (설계서 §3, 단계 1)
python main.py initdb --db kbo.db

# N경기 시뮬레이션으로 판단 (모듈 3~6). 3개 시나리오 비교:
python main.py simulate --games 5000 --scenario all --seed 42 --report-dir out
```

## 시나리오와 해석

시장은 (놓치는 정보를 제외하면) 진짜 확률을 아는 **효율적 벤치마크**로 모델링한다.
우리의 엣지는 오직 시장이 놓치는 변수(설계서 §2가 지목한 **불펜·일정 피로**)에서만 나온다.

| 시나리오 | 설정 | 기대 결과 |
|---|---|---|
| `edge`  | 시장이 피로의 70%를 놓침 + 모델은 거의 정확 | **GO**, ROI(+) |
| `fair`  | 시장이 모든 걸 정확히 봄(=진짜 확률) + 모델은 약간 노이즈 | **NO-GO**, ROI ≈ −마진 |
| `worse` | 시장 정확 + 모델이 매우 노이즈(틀림) | **NO-GO**, ROI ≈ −마진 |

실행 예시 출력(5000경기, seed 42):

```
scenario   GO?  model_LL   mkt_LL   bets       ROI
edge        GO    0.4730   0.5266   6930  +28.94%
fair     NO-GO    0.5330   0.4989   5757   -5.61%
worse    NO-GO    0.7662   0.4989   7239   -5.31%
```

**핵심 판단**: 모델이 시장을 *진짜* 이길 때만(`edge`) ROI(+)·GO 가 나오고, 정보 우위가
없으면(`fair`/`worse`) 마진(~−4.8%)만큼 잃으며 NO-GO 로 막힌다. 이것이 설계서 §5 경고
("시장과 어긋남 = 대개 내 모델이 틀림")와 §6 GO/NO-GO 게이트의 실증이다.

> 참고: `edge` 의 ROI 크기는 *시장이 피로를 얼마나 놓치느냐*에 비례한다. 위 예시는
> 70% 를 놓치는 다소 큰 엣지를 가정한 것으로, 실제 시장은 더 효율적이라 엣지는
> 훨씬 작거나 없을 수 있다.

## 아키텍처 (설계서 §1)

```
kbo/
  store/      스키마(§3) + SQLite 초기화/헬퍼          [모듈 2]
  model/      포아송 λ 추정 → 득점분포 → 3종 마켓 확률  [모듈 3, §4]
  ev/         EV 계산 + 시뮬용 북메이커(마진)          [모듈 4, §5]
  backtest/   log-loss/Brier/캘리브레이션 + GO/NO-GO    [모듈 5, §6]
  sim/        진짜 세계 생성 → N경기 → 리포트(핵심)
  crawler/    Statiz·KBO 수집 — 인터페이스 stub         [모듈 1, §2]
  scheduler/  디스코드 포맷터(구현) + 잡/전송 stub      [모듈 5, §7]
main.py       CLI (initdb / simulate)
```

### 예측 모델 (포아송 결합, §4)

- `λ = 리그평균 × 홈어드밴티지 × 파크팩터 × exp(상대선발억제 + 자기타선 + 상대불펜피로 − 자기일정피로)`
- 득점 ~ Poisson(λ) (분산 과대 시 음이항 옵션)
- 두 팀 분포 결합 → P(승), P(오버), P(핸디 커버)

### EV 엔진 (§5)

```
공정배당 = 1 / model_prob
EV = model_prob × 실제배당 − 1
EV > threshold(기본 0.05) 인 마켓만 후보
```

### 신뢰도 게이트 (§5·§6)

백테스트에서 **(1) 모델 log-loss < 시장 baseline** 그리고 **(2) 캘리브레이션 오차 < 0.05**
를 모두 만족할 때만 `passed=True`(GO). 미달 시 실전 신호 비활성.

## 미구현(stub)과 다음 단계 (설계서 §8)

- `crawler/`: Statiz·KBO 크롤러는 **계약(반환 스키마)만** 정의. 실제 구현 시 robots.txt
  준수, 요청 간 2~5초 지연, User-Agent 설정, 개인 용도 한정 필수.
- `scheduler/`: 디스코드 **메시지 포맷터는 구현**(테스트됨), 웹훅 전송·APScheduler
  잡 등록은 stub.
- 다음: 과거 시즌 적재 → 실데이터 백테스트 → (통과 시) 수동 배당 입력 + 발송.
  **5단계 백테스트 실패 시 실전 발송 단계로 넘어가지 말 것.**

## 테스트

```bash
python -m pytest -q
```

포아송 마켓 단조성·합, EV 공식(설계서 §5 예시 값), 지표(완벽예측 Brier=0,
무작위 log-loss≈ln2), 시뮬 재현성·대수의 법칙·시나리오 방향성을 검증한다.
